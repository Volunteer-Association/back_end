Architecture Review · Payment Readiness

从「内部记账钱包」到「支付宝 / 微信 真实支付体系」

本报告基于对前后端代码的逐模块审查（NestJS 后端 85 个 TypeScript 文件、Vue3 前端 24 个视图），评估当前工程架构、模块化程度，并对照支付宝开放平台与微信支付 V3 的标准能力，列出对接真实支付前必须补齐的功能与后台管理项，给出可落地的分阶段改造路线。

后端：NestJS 12 · TypeORM · MySQL · JWT 前端：Vue 3 · Vite · Element Plus · Pinia 生成日期：2026-10-18
核心结论

当前系统已经实现了一套工程质量不错的「站内余额钱包」（事务、悲观锁、流水账、幂等、风控、对账都在），但与支付宝 / 微信的真实网关对接度为 0——「alipay / wechat」目前只是线下转账的一个标签，充值靠人工审核加钱、提现靠人工标记打款，没有下单接口、支付二维码、异步回调、验签、退款网关、对账文件和代付。要走向真实支付，需要新增一层支付渠道适配层与配套的订单 / 回调 / 退款 / 对账 / 代付体系，并补齐后台资金中心。

一句话判断：地基扎实，缺的是「支付网关」这一层和围绕它的资金运营后台

值得保留

金额用「分」整数存储、事务 + 悲观行锁防超扣、每笔变动写流水、幂等键、雪花单号、支付密码、风控限额、人工对账修复——这些是支付系统的正确内核，对接真实渠道时直接复用。

需要重构

支付域巨型 Service、授权校验散落（已统一）、缺少渠道适配层与统一订单模型、用 setInterval 做定时任务、前端视图平铺、演示页与业务混杂。

必须新建

收单下单 / 回调验签 / 退款 / 对账 / 代付（自动提现）/ 分账 / 证书密钥管理，以及后台的交易中心、退款中心、对账中心、渠道配置与资金报表。

本次已直接修复一处支付上线前必须堵的安全问题：新增统一的 RolesGuard + @Roles() 声明式授权，并给 3 个「只登录就能访问」的管理员接口补上管理员校验（已通过 tsc --noEmit 类型检查）。详见第 02 节。

02

架构与安全问题

按严重程度排列。P0 为安全问题（已在本次修复），P1 为对接支付前必须做的结构性重构，P2 为工程化增强。

P0 · 越权漏洞（已修复）—— 授权逻辑散落、有遗漏

根因：AuthGuard 只做「认证」（登录态），「授权」（是否管理员）靠每个控制器方法手写 assertAdmin() / requireAdmin()，一旦漏写就是越权。

P0
提现审批越权：普通用户可批准任意提现

src/modules/payments/admin-withdraw.controller.ts · GET/POST admin/withdraw/*

待打款列表、手续费统计、批准打款、拒绝退回 4 个接口只有 @UseGuards(AuthGuard)，没有任何角色校验。任何登录用户都能查看待打款列表，并可直接批准自己的提现（无需真实打款就把流程走完）。

已修复：类级追加 @Roles('admin') + RolesGuard。
P0
风控配置越权：普通用户可自行改限额

src/modules/payments/admin-risk.controller.ts · GET/PUT admin/risk-config

转账 / 提现单笔、日累计限额属于风控红线，任何登录用户都能读取甚至修改（例如把转账限额改成无限大），风控形同虚设。

已修复：类级追加 @Roles('admin') + RolesGuard。
P0
系统监控越权：服务器指标泄露

src/modules/system/system.controller.ts · GET admin/system/metrics

CPU、内存、磁盘、网络流量、磁盘 IO 等主机监控信息，任何登录用户都能拉取，便于攻击者侦察。

已修复：类级追加 @Roles('admin') + RolesGuard。
修复方式（标准 NestJS 做法）：新增 src/decorators/roles.decorator.ts 与 src/guards/roles.guard.ts，用 @UseGuards(AuthGuard, RolesGuard) + @Roles('admin' | 'super_admin') 声明式收口，角色按 super_admin > admin > user 层级比较。建议后续把所有 admin 控制器从手写判断统一迁移到该装饰器。

P2 · 工程化与能力缺口

无 Redis

幂等、限流、验证码、锁、缓存全部压在 MySQL；支付回调高并发、扫码轮询、分布式锁都依赖 Redis，建议引入（或 Redlock）。

无消息队列

异步通知、回调后置入账、对账、退款/代付重试、通知下发应异步化，建议 BullMQ（基于 Redis）或接入云消息队列。

无支付配置位

.env 中没有支付宝 / 微信的 APP_ID、商户号、APIv3 密钥、应用私钥、平台证书、回调地址，密钥也没有加密存储方案。

通知渠道单一

支付成功/失败、到账、退款、代付结果仅站内信；真实支付需要短信、微信公众号/小程序模板消息、APP 推送。

审核人记录有误

admin-withdraw 取 req.user.username，而 AuthGuard 只挂 sub/roles/role，取不到值会恒为 'admin'，导致提现审核人无法追溯。应改用 sub 或补充用户名。

无幂等兜底在网关层

已有 idempotency_keys 表，但真实支付回调（可能重复推送、乱序）需要「验签 + 状态机 + 唯一约束 + 日志」四重幂等，目前只在业务申请层有。

04

支付渠道适配层设计

用一个统一接口屏蔽支付宝与微信的差异，业务层只面向接口编程；先实现 MockGateway 跑通全链路，再接真实沙箱。

4.1 统一网关接口（建议契约）

// modules/payments/gateway/payment-gateway.interface.ts
export interface PaymentGateway {
  readonly channel: 'alipay' | 'wechat';
  /** 统一下单：按场景返回二维码串 / 跳转URL / JSAPI(prepay)参数 */
  createPayment(cmd: CreatePaymentCmd): Promise<PaymentCredential>;
  /** 主动查单（回调丢失时的兜底补偿） */
  queryOrder(outTradeNo: string): Promise<GatewayOrderResult>;
  /** 关闭未支付订单（超时关单，防止重复支付） */
  closeOrder(outTradeNo: string): Promise<void>;
  /** 验证异步通知签名并解密（微信 APIv3 需 AES-GCM 解密），返回标准化结果 */
  parseAndVerifyNotify(raw: Buffer, headers: Record<string,string>): Promise<NotifyResult>;
  /** 退款（支持部分退，out_request_no 幂等） */
  refund(cmd: RefundCmd): Promise<RefundResult>;
  queryRefund(refundNo: string): Promise<RefundResult>;
  /** 代付 / 提现到账（微信商家转账到零钱、支付宝单笔转账） */
  transfer(cmd: PayoutCmd): Promise<PayoutResult>;
  /** 下载并解析对账单（交易账单 / 资金账单） */
  downloadBill(date: string, type: 'trade'|'fund'): Promise<BillRecord[]>;
  /** 生成 / 应答回调（success / 应答报文） */
  ackNotify(): string | { code: string };
}

4.3 收单闭环（一笔真实充值的完整链路）

1
下单
用户选渠道/场景，后端建 payment_order（幂等），调 gateway.createPayment 拿二维码/JSAPI 参数
2
支付
前端展示二维码或拉起支付宝/微信，用户完成付款
3
异步通知
渠道回调 notify_url，后端验签→解密→记日志→状态机判断→幂等入账→应答
4
兜底查单
前端轮询 + 后端定时 queryOrder 补偿漏单；超时未支付 closeOrder
5
入账
OrderService 调 WalletLedger：余额 += 金额、写 recharge 流水（与现有内核一致）
6
通知
站内信 + 短信/模板消息告知到账
7
退款
原路退回（退款单 + 退款回调 + 扣回余额）
8
对账
T+1 下载渠道账单，与系统订单/流水三方勾对账

4.4 统一订单状态机（内部支付单，不复用线下审核单）

CREATED ──支付成功(notify/query)──▶ PAID ──全额退款──▶ REFUNDED
   │                                └──部分退款──▶ PARTIAL_REFUNDED
   ├──用户取消/超时(关单)──▶ CLOSED
   └──支付失败/渠道异常──▶ FAILED（记录原因，允许重新发起）
// 状态流转必须在事务内 + 行锁，且仅允许上述合法迁移；重复 notify 命中 PAID 直接幂等返回，不重复入账。

07

数据模型新增建议

真实支付与「线下审核单」是两套单据，建议新增而非改造 recharge_orders，避免污染现有人工流程。所有金额继续沿用「分」整数 + 业务单号 + 幂等。

新增表关键字段 / 作用
payment_orders 统一收单订单out_trade_no（唯一）、user_id、scene、channel、subject、amount_cents、status 状态机、channel_trade_no（渠道单号）、prepay_id/credential、paid_at、expired_at、fee_cents、idempotency_key、商户号、唯一索引(channel,channel_trade_no)
payment_notify_logs 回调日志channel、out_trade_no、notify_id、原始报文、请求头、验签结果、解密结果、处理状态、处理耗时、接收时间；用于排障与幂等
payment_refunds 退款单out_refund_no（唯一）、out_trade_no、total/refund_cents、reason、status、channel_refund_no、success_time、审核人、部分退次数
payout_orders 代付单提现/转账到零钱，扩展现有 withdrawals：payee 账户（openid/支付宝账号/银行卡）、渠道批次号、status、回单号、失败原因、重试次数
channel_accounts 渠道商户配置channel、mch_id、app_id、商户私钥/APIv3Key/证书（KMS 加密存储）、env(sandbox/prod)、notify_url、费率、启用状态、多租户/多商户
reconcile_batches / _items对账批次（日期/渠道/账单文件）与明细勾对：系统单 vs 渠道单，差异类型（长款/短款/错金额/状态不符）、处理状态
risk_events / blacklist风控命中事件、规则快照、黑名单（用户/设备/账户），与现有 risk_configs 配合
split_* （P3）分账接收方、分账订单与明细，仅在平台抽佣多方分账时需要
关系：payment_orders 支付成功后调用现有 balance_transactions（recharge 流水）入账；refunds 退款成功后写 consume/refund 流水；payout_orders 与现有 withdrawals 共用 Ledger。这样既不动现有记账内核，又能把「真实渠道单据」与「站内资金流水」通过 ref_type/ref_id 关联，天然可对账。
